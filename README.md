# DockerUpdate v7.0.4 · 镜像更新页「更新并重建容器」

## 本版新增

- **镜像更新页第二种模式**：原来只有「更新选中」（只拉取镜像、不动容器），现新增「更新并重建容器」——拉取新镜像后，自动找出使用该镜像的所有容器，按原配置重建，使新镜像立即生效。顶部批量按钮与每行操作列各有一枚，沿用 v6.0-r20 规则：**只有检测到可更新版本才显示**。
- **重建前先看影响面**：点击后先调 `image-rebuild-plan`（只算不写），二次确认里给出「将更新 N 个镜像、重建 M 个容器」的真实数量；面板自身容器、带排除标签的容器、`_du_old` 临时备份容器一律跳过并列明原因。
- **重建不丢配置**：复用 `manager.build_create_body` + `manager._recreate`，端口、环境变量、卷 / 挂载、网络、标签、重启策略、资源限额、命令与入口点全部保留；重建前先生成版本备份，支持「更新后健康检查」，不通过按旧镜像 ID 自动回退。
- **两种可选行为**：镜像 ID 未变化且未勾选「镜像无变化也重建」时不中断任何容器；本机没有容器使用该镜像时只更新镜像并如实说明。工具栏新增「镜像无变化也重建」开关。
- **进度条明细**：拉取、匹配容器、备份、重建、健康检查、回退逐行写进运行明细（含 Docker API 路径与镜像 ID），异步任务走 SSE 增量行，不重建 DOM，不会重现「转圈时整页闪」。
- **状态与通知同步**：拉取结果写回 `image_updates.json`，容器检测状态标记已更新，成功 / 失败 / 自动回退分别走 `update_ok` / `update_fail` / `auto_rollback` 既有事件开关，并写运行日志；没有新增事件项，告警页开关数量不变。
- **版本统一 v7.0.4**：`config.APP_VERSION`、界面徽章、登录页、HTTP Server 头、部署脚本、README 与「通知自检」模块标记全部一致；`docker-compose.yml` 与挂载一个字节没改，`data/` 结构不变。

部署：`scp` 升级包到 `/vol1/1000/docker/` → `unzip -o` → `cd docker-update && sh deploy.sh` → 浏览器 `Ctrl+F5`，确认徽章 `v7.0.4`。只覆盖文件不重建容器，进程里仍是旧模块。

# DockerUpdate v7.0.3 · P4 柔灰雕塑 UI 与四项 BUG 修复

## 本版新增

- **功能总开关**：「容器 → 目录映射 → 新容器默认映射模板」面板右上角新增一颗总开关，编辑弹窗里也有同步开关。它控制的是**整个「后续新容器自动套模板」功能**：关闭时后台巡检只登记容器基线，绝不写映射、绝不重建容器、不发继承事件；开启后原有的「自动继承 / 继承后自动重建 / 预迁移 / 排除名单」子开关才恢复生效。
- **默认关闭，升级零影响**：`policy.master` 默认 `False`。从任何旧版覆盖升级后，现有容器、已配好的模板与已继承配置一个都不动；想用还得手动打开总开关。
- **不会误清配置**：总开关走独立接口 `mounts-master`，只改 `policy.master`，不重写 `doc["template"]`；模板行、子开关、排除名单、已登记容器与已继承记录全部原样保留。「立即扫描新容器」在总开关关闭时会明确返回「本轮仅登记基线，未套模板」。
- **版本统一 v7.0.3**：`config.APP_VERSION`、界面徽章、登录页、部署脚本、README 与「通知自检」的模块标记（跟随 `APP_VERSION` 自动变化）全部一致。
- **进度条显示后台运行明细**：更新、删除、拉取、目录映射应用、后台巡检等走进度条的操作，浮层里逐行显示服务端实际执行——HTTP 入口与参数摘要（密码 / 令牌脱敏）、每一次 Docker Engine API 调用（方法、路径、状态码、耗时、字节数）、业务阶段与结果、异常与终态。异步任务走 SSE 增量行，同步请求与后台巡检走 `/api/trace` 轮询；按 `seq` 增量追加 DOM，不重建，不会再出现「转圈时整页闪」。支持折叠、一键复制全部明细、随时收起。
- **顺带修掉一个显示问题**：映射行与模板行的启用开关原先渲染成 `<i>`，但全局开关样式用的是 `.track`，导致轨道不显示；现已统一为 `.track` 并补了表格内开关的去边框规则。

下方保留 v6.0-r24 / r25 的目录映射功能说明（两步生效、重建不丢配置、数据预迁移、安全边界、通知日志备份等），这些能力本版全部保留。

部署方式与历史版本一致，详见下方各版本章节。

>    时补进程名；KPI、筛选、搜索、指定端口占用检查、疑似冲突提示齐全。
>    不结束进程、不改防火墙、不占用端口；未挂 `/host` 时如实标注「仅面板容器可见」。

>    **物理限制如实说明**：真正断网时企业微信 / 钉钉等云端 Webhook 也发不出去，因此
>    断网瞬间会同步尝试「内网 / 局域网通知地址」，并把未送达的消息排队，恢复后自动补发；

>    都在告警页可见，可手动「立即探测」与「测试断网 / 恢复通知」。

>    属性名时 Python 抛 `getattr(): attribute name must be string`，于是 `ports`、
>    `ports-check`、`netwatch-save`、`netwatch-test`，以及更早的 `yaml-check`、
>    `yaml-format`、`audit-clear` 等分支在**真实服务**里一律 500；浏览器预览用的模拟层
>    没走这条路径，所以此前没被发现。现在先按 `callable()` 分流：lambda 直接调用，
>    字符串才绑定 `self` 的方法。真实 HTTP 逐个复测 7 个分支全部 200，新增 6 个接口
>    的 401 拦截与畸形参数 400 也一并验证。

## v5.0（重大版本：镜像级选源 / 更新后健康检查自动回退 / 多渠道通知）

相对 v3.9-r7，这是一次功能性大版本升级，`docker-compose.yml` 与挂载**完全不变**，覆盖升级即可。

- **镜像级智能选源**（解决「源很多，但有的源没有我的容器」）：「系统联动 → 加速源 → 按容器检测」会读取本机所有容器用到的 `repo:tag`，逐个对 Docker 镜像源做 manifest 探测，确认「这个源真的收录了这个镜像」再比延迟。结果给出每个镜像的可用源数、最快源、可直接复制的 `docker pull <前缀>/<镜像>` 命令，以及覆盖你镜像最多的 3~5 个源组成的推荐 `daemon.json`。严格预算：默认 10 源 × 20 镜像、24 并发、单请求 2.5 秒；返回 200 的 HTML 错误页不会被误判成「有镜像」。
- **加速源列表管理**：新增本地搜索、状态筛选（正常 / 限流 / 失败 / 未测）、「仅测未测」与「按容器检测」入口；过滤只切 CSS、不重建 DOM，不会重现以前「输入被自动刷新冲掉」。每个 Docker 源显示「收录 N 个」覆盖数。r7 的批量添加（自动按行区分、三类目标、逐行反馈）与 117 个候选源全部保留。
- **更新后健康检查 + 自动回退**：设置页新增一节，可选「仅容器运行中 / HTTP / TCP」探针，可配端口、路径、等待、超时、重试。更新重建后按配置探测，不通过且开启自动回退就立刻调用已有的备份回退链路恢复旧版本，写运行日志并推送通知。HTTP 把 4xx（多半是要求登录）视为服务有响应，只有连接失败 / 超时 / 5xx 算异常；没有端口映射自动降级为运行状态检查。
- **多渠道通知**：通知中心从单 Webhook 升级为可同时启用自定义 Webhook / 企业微信 / 钉钉 / 飞书 / Telegram / Bark / Server 酱；支持钉钉与飞书加签、逐渠道返回结果、按事件开关（更新成功 / 失败 / 自动回退 / 发现新版 / 容器异常 / 检测失败）。旧版 `notify.json` 单渠道配置自动迁移，不丢。面板不内置任何地址或凭据，未配置就明确显示「未配置」。
- 版本号统一为 `v5.0`（界面、HTTP Server 头、部署脚本、说明）。

**边界**：镜像探测走匿名 manifest 请求，私有仓库 / 需鉴权源会如实标「需要鉴权」，不伪造可用；公共公益源随时可能限流、白名单化或关停，探测结果只代表「此刻」。面板只读挂载宿主机根目录，不会替你写 `/etc/docker/daemon.json`。健康检查依赖「更新前自动备份」开启，否则回退没有快照可用。

## 三·补零 · v3.7 使用说明

### 运行日志 / 动画
顶部「运行日志」现在是独立页面，展示最近 60 条检测、备份、更新与容器操作，红色为失败；「设置」「运行日志」点亮时会高亮。切页、弹窗、抽屉、toast、按钮与卡片 hover 都有 0.2~0.3 秒过渡，视图容器本身不随轮询重建，所以不会像以前那样周期性闪。

### 落盘位置为什么以前会「自己变回默认」
`renderSystem()` 每次自动轮询都会用服务端旧的 `P.settings` 重新生成三个输入框；用户填完还没保存、或保存后 `/api/pro/state` 回读慢时，就会被旧值覆盖。v3.7 引入会话草稿 `duStorageDraft`：`oninput` / 「浏览」回填都写草稿，未保存时跳过轮询重绘；保存成功后用 `save_settings` 回显的 `settings` 直接更新本地状态并清草稿，同时在页面底部打印三个已保存路径。按「恢复当前已保存值」可丢弃草稿。

### 计划任务（18 种）
类型 / 目标是否需要 / 候选容器名、栈名、镜像名全部由 `task-options` 从真实 Docker 状态带出，不用凭记忆敲。18 种：重启 / 启动 / 停止 / 暂停 / 恢复指定容器、重启全部运行中容器、重启 Compose 栈、清理悬空镜像、清理孤立卷、备份 Compose、检查镜像更新、全量巡检（含自动更新）、拉取指定镜像最新版、导出容器日志、健康巡检并推送、更新前备份指定容器、备份面板数据、测试通知推送。调度支持每天固定时间、每隔 N 分钟、每周几固定时间；可编辑、启停、立即执行、删除，执行历史记录成功与失败。每个动作都有真实后端实现，失败如实返回原因并写进历史。

## 三·补一 · v3.6 使用说明

### 全部镜像源一起获取、自动选最快仓库

## 四、必须说清的能力边界

1. **fnOS 私有接口不伪造**：原生桌面图标、通知中心、系统账号没有公开地址，面板只提供「快捷方式文件 / Webhook」两种适配器与网关配置入口。没填就显示「未配置 / 已跳过」，不会假装成功。
2. **Compose 是受限解析**：支持 `services / image / ports / volumes / environment / restart / command / labels / network_mode / privileged / user / read_only / mem_limit / depends_on`；不支持 `build:`、anchors、extends、多行块、`include`，遇到会明确报错，不会静默丢配置。生成的 `docker-compose.yml` 仍写进可写根，方便在飞牛 GUI 里接着用。
3. **容器内没有 `docker compose` 二进制**：`up` 是逐服务调用 Docker Engine API 创建并启动容器，不是执行 compose CLI。
4. **镜像实际存储位置由 Docker daemon 的 `data-root` 决定**：面板不能改；可改的是容器配置 / Compose 文件 / 绑定数据卷的落盘目录（系统联动 → 存储，默认 `/vol1/1000/docker/compose-stacks` 与 `/vol1/1000/docker/apps`）。
5. **Web 终端是 HTTP 轮询桥接，不是 WebSocket**：输出约 300ms 追加一次，`vim` / `top` 等全屏程序体验有限，复杂操作建议 SSH。
6. **Docker Hub 搜索接口**：`GET https://hub.docker.com/v2/search/repositories/?query=&page=&page_size=`，公开免登录；国内直连超时会自动回退内置官方目录，不再显示空白页。私有 Registry V2 没有关键词搜索，只有 `_catalog` 列名 + `tags/list`（按名称过滤）。内置 93 项是离线快照，不等于官方实时 2500+ 项全量。
7. **镜像仓库 / 应用模板拉镜像走的还是 NAS 的 Docker daemon**：`registry-1.docker.io/v2/ ... Client.Timeout exceeded` 属于 daemon 网络层，面板调超时只能多等，根治要在 NAS 上配代理或仍可用的 registry mirror（`daemon.json` 后重启 Docker）。面板里的 GitHub 加速源只加速索引 / README / 图标，不改 daemon。

### 2. Web 终端所有容器都连不上（真 BUG）

报错 `Remote end closed connection without response`。根因是 `TermSession` 用
`UnixHTTPConnection(timeout=0)`：Python 把 `timeout=0` 当成**非阻塞 socket**，
`getresponse()` 读不到 HTTP 响应头就抛 `RemoteDisconnected`；且 `http.client` 的
`makefile` 缓冲会吞掉响应头之后的首批终端输出。

现在改为**直接握原始 UNIX socket**：自己发 `POST /exec/{id}/start` 带
`Connection: Upgrade`，自己解析响应头，剩余字节直接进终端缓冲区（首批提示符不丢），
读完再把 socket 设为 0.4s 超时供读线程使用。单元测试用模拟 Docker daemon
验证了 Upgrade 头、ConsoleSize、首行 `sh-5.1# ` 与命令写入。

### 3.「进程」与「Inspect JSON」报「容器不存在: {'name': 'lucky'}」（真 BUG）

`Pro.action()` 统一把整个 `body` dict 传给方法，但 `process / inspect / netio`
三个方法声明的是 `def xxx(self, name)`（字符串），于是 `_cid` 收到
`{'name': 'lucky'}` 这个字典，永远匹配不上容器名。现在三个方法改收 `body`，
统一用 `_name()` 抽出容器名；`_cid` 同时支持按名字 / 完整 ID / ID 前缀查找，
`action()` 对非 dict 入参也做了兜底，畸形参数不会再 500。

### 4. 端口占用只显示 2 个（真 BUG）

`/proc/net` 是**当前进程所属 netns** 的视图（内核里等价于 `/proc/self/net`）。
即使 compose 挂了 `/:/host:ro`，读 `/host/proc/net/tcp` 拿到的仍是
**面板容器自己**的命名空间——所以只看到 10000 与 127.0.0.11（Docker 内嵌 DNS），
`source` 却误标成「整机视角」。

现在优先读 `/host/proc/1/net/{tcp,tcp6,udp,udp6}`（宿主机 PID 1 的 netns = 整机视角），
逐级回退并如实标注数据来源。另按 Docker 端口映射补全所有已发布端口：
某些 NAS 上 PID 1 的 netns 受权限限制读不到，但 `docker.sock` 一定知道容器映射，
不能让整机视图只剩面板自己。测试构造 4 个监听 + 2 条连接态 + 3 个容器映射，
实测从「2 个」变成 6 行，TIME_WAIT 不再被算成占用。

### 5. 目录映射两列路径按钮（真 BUG）

`#i-folder` 这个 SVG symbol **根本没在 `index.html` 里定义**，所以第一列按钮里的
`<use>` 渲染成空白方块；第二列压根没生成按钮。现在补上 `i-folder` / `i-folder-in`
两个 symbol，两列各一枚 34px 按钮、图标统一 18px；第二列新增「选择容器内路径」
弹窗（常用路径 + 该容器现有挂载的容器侧路径 + 自由输入），因为容器内路径
不在宿主机文件系统里，不能套用目录树。

### 6. 软链接与映射的区分（概念澄清，不是 BUG）

**两者不是一回事**：
- **目录映射**（本页）= 把飞牛上的**整个文件夹** bind mount 进容器指定路径，两端路径自定义，
  需要「应用并重建」才生效；
- **文件软链接**（容器 → 子标签「文件软链接（A→B 改名）」）= 把飞牛上的**单个 A 文件**，
  用容器只认得的 **B 文件名**放进去（软链接或同步副本），可设执行周期自动补建。

v7.0.2 就有独立的 `symlinks.py / symlinks.js` 页面，但入口文案容易和映射混在一起。
v7.0.3 把两个子标签分别改成「目录映射（文件夹）」与「文件软链接（A→B 改名）」，
并在目录映射页顶部加了一句说明和一键跳转按钮。

### 部署与兼容

`docker-compose.yml` 与挂载（`/:/host:ro`、`/var/run/docker.sock`、`/store`）一个字节没改，
`data/` 结构不变，覆盖源码后执行 `sh deploy.sh` 重建容器，浏览器按一次 `Ctrl+F5`。

## v6.0-r25 变更（后续新添加的容器也能自动用上目录映射）

上一版 r24 的「目录映射」只对**当时已经存在、且手动配置过**的容器生效。这一版补上「以后新建的容器」：

- **默认映射模板**：在「容器 → 目录映射」页配置一组飞牛目录 → 容器内路径，作为所有后续新容器的默认值；两端路径都仍可自定义，支持 `{name}`（容器名）与 `{image}`（镜像短名）占位符，例如 `/vol1/1000/docker/appdata/{name}:/data` 让每个新容器各用各的文件夹。
- **自动继承开关**：默认**关闭**。开启后，后台每 30 秒登记一次容器，凡是在飞牛 GUI、Compose、`docker run` 里**新出现**的容器，都会自动获得这份模板配置；不需要打开面板页面，也不需要手动点保存。
- **同名重建也会跟上**：容器被删掉再建、或 Compose `down/up` 导致容器 ID 变化但名字不变时，会重新套用模板并清空旧的「已应用」记录，避免把上一个容器的挂载误判成当前挂载。用户手工改过的配置永远不会被模板覆盖。
- **可选自动应用**：默认只写配置、不碰容器；开启「继承后自动应用并重建」才会自动重建（会短暂中断，每轮最多 2 个，失败只记录不中断其它容器）。保守起见，面板自身容器、排除名单里的容器一律跳过。
- **升级绝不重建老容器**：首次后台巡检写入 `baseline_done` 标记，只把当前已存在的容器登记为「已知」；即使先配好模板再重启面板，也不会把老容器误判成新容器。之后出现的才算新容器，因此升级 r25 不会动任何现有容器。
- 新增 `mounts-template` / `mounts-template-save` / `mounts-sync` 三个接口、一个 `mount_inherit` 可选推送事件；模板、策略与登记表仍全部存在 `data/pro/container-mounts.json`，随面板备份导出 / 恢复。
- 修掉一个边界：r24 成功应用后把容器**名字**存成了 `container_id`，外部同名重建后 `plan()` 会拿旧记录里的 binds 当受管挂载；现在存真实容器 ID，且 ID 不匹配时自动失效旧记录。
